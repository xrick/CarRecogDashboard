# 需求規格：白/黑名單本地持久化（唯讀鏡像）

**日期**：2026-05-18 ｜ **優先級**：最高（先前估算 G1）｜ **狀態**：需求確認完成，待 `/sc:design`
**產出自**：`/sc:brainstorm` — 僅需求發現，未做架構/schema/實作決策。

## 1. 問題背景
- 現況：名單存於 `IngestManager._lists`（記憶體），**重啟即失**；冷啟後到第一次輪詢前，所有車輛被誤判為「陌生」。
- 名單僅在向相機 `recordFinder.cgi?action=find&name=TrafficRedList|TrafficBlackList`（§10.3.4，已於 .10 實機驗證 200）成功輪詢時更新；看板本身從不修改名單。
- V3.87 無「寫進我方 SQLite」之 API；SQLite 持久化是本專案自有程式碼。`recordUpdater.cgi` 寫的是*相機*名單，且規格 §10/§2 禁止看板改名單。

## 2. 已確認決策（本次 brainstorm）
- **D1 唯讀鏡像**：相機為唯一權威來源；SQLite 僅本地鏡像/快取；**不寫回相機**（遵循規格 §10/§2）。
- **D2 更新策略**：每次輪詢成功 → 差異偵測；**僅在內容有變動時**才以全量快照取代寫入。
- **D3 顆度**：以**相機 host 為鍵**，各相機獨立的紅/黑名單快照。
- **D4 防呆（最終 2026-05-18：found=0 一律保留不覆蓋）**：
  - **抓取失敗**（連線/HTTP 錯誤、逾時）→ **不覆蓋**上次良好快照；標 stale + 最後同步時間。
  - **抓取成功但 `found=0`** → 同樣**不覆蓋**既有快照（**永不因 `found=0` 自動清空**）；標 stale/註記。
  取捨（已知並接受）：好處是相機短暫異常回 `found=0` 不會誤清名單；代價是若相機名單**真的被清空**，本地鏡像不會自動反映（需人工/明確機制，列殘留 R-2）。
- **D5 全新未同步狀態**：SQLite 從未有過該 host 快照（全新部署）→ 分類進入「名單未同步（系統安裝中）」狀態，不標記為「陌生」、不發陌生告警；待首次成功同步後才正常分類。
- **D6 過期上告警牆**：名單超過新鮮度門檻 → 於異常事件牆顯示「名單過期/未同步」告警卡（沿用既有 api_delay 卡片模式）。

## 3. 目標
- G-1 重啟後立即以「最後良好名單」做事件分類，消除冷啟誤判窗。
- G-2 相機/recordFinder 暫時不可達時，分類仍可運作且明確顯示資料新鮮度。
- G-3 名單變動可被偵測（為日後 audit/告警預留；本期不一定實作歷史）。

## 4. 功能需求（FR）
- **FR-1** 啟動時由 SQLite 載入各 host 的紅/黑名單至記憶體鏡像，先於第一次輪詢即可分類。
- **FR-2** 輪詢成功後比對新名單與既有快照；**僅當有差異**才以新全量快照取代並更新「最後同步時間」。
- **FR-3** 內容無差異 → 不寫 SQLite；僅更新「最後檢查時間」，且與過期判定一致。
- **FR-4** 抓取失敗（連線/HTTP 錯誤/逾時）→ 保留 SQLite 與記憶體既有快照；該 host 名單標記為 stale（不清空）。
- **FR-5** 抓取**成功**且 `found=0` → **不覆蓋**既有快照（與 FR-4 一致）；**永不因 `found=0` 自動清空**；標 stale/註記最後同步時間。
- **FR-6** 事件分類以「記憶體鏡像」為準，該鏡像於啟動時由 SQLite 補水（hydrate），兩者保持一致。
- **FR-7** 紅名單／黑名單／host 三者組合各自獨立儲存與更新。
- **FR-8** **只儲存 `PlateNumber`**（不存車主/車種/OpenGate 等其餘 §10.3.4 欄位）。
- **FR-9** 新鮮度可視：可得知每 host 名單「最後成功同步時間」與「是否過期」。
- **FR-10** 全新未同步：SQLite 無該 host 快照時，分類回傳「名單未同步（系統安裝中）」狀態，**不**判為「陌生」、**不**發陌生告警；首次成功同步後恢復正常。
- **FR-11** 過期判定 + 告警牆：名單距最後成功同步超過新鮮度門檻 → 標記過期，並在異常事件牆顯示「名單過期/未同步」告警卡。門檻預設 **2 × poll_interval**（可調，見殘留項 R-1）。

## 5. 非功能需求（NFR）
- **NFR-1** 一致性：補水與寫入需在多相機 thread + 請求並發下保持一致（沿用既有 SQLite 寫鎖）。
- **NFR-2** 效能：差異偵測/寫入為 O(名單大小)（通常 < 數千筆），不得阻塞事件串流。
- **NFR-3** 原子性：全量快照取代不可出現半套狀態。
- **NFR-4** 安全/PII：本期**只存車牌、直接保留**，不另做遮罩/加密/保留期限控制（使用者決策）。
- **NFR-5** 規格相容：不得提供任何寫回相機名單之路徑（遵 §10）。

## 6. User Stories / 驗收準則
- **US-1**（現場警衛）重啟後第一台車經過即正確顯示白/黑分類。
  - AC：重啟後、第一次輪詢前送一筆已知白名單車牌事件 → 分類為「白名單」。
- **US-2**（值班人員）recordFinder 不可達時仍以最後良好名單分類，狀態列顯示「名單最後同步 hh:mm · 可能過期」。
  - AC：模擬 recordFinder 失敗 → 既有快照不被清空；顯示 stale 與最後同步時間。
- **US-3**（維運）名單無變動時不產生無謂 DB 寫入。
  - AC：連續兩次輪詢內容相同 → 名單資料列無變更（寫入 0 次）。
- **US-4**（維運）名單有變動時，重啟後依新版名單分類。
  - AC：相機新增一筆 → 輪詢後 SQLite 更新 → 重啟 → 該車牌分類正確。
- **US-5**（值班人員）相機某次回 `found=0` 時，不可誤清本地名單。
  - AC：recordFinder 成功回 `found=0` → 該 host 既有快照**維持不變**，分類仍用既有名單；標註該名單可能過期。
- **US-6**（現場警衛）全新部署、系統安裝中且相機尚未同步過 → 不應整片誤判為「陌生」。
  - AC：SQLite 無任何快照且相機不可達 → 事件顯示「名單未同步（系統安裝中）」狀態，不產生陌生告警。
- **US-7**（值班人員）名單過期需在告警牆看得到。
  - AC：最後成功同步距今 > 2×poll_interval → 異常事件牆出現「名單過期/未同步」卡並顯示最後同步時間。

## 7. 範圍邊界
- **In scope**：紅/黑名單讀取鏡像、SQLite 持久化、啟動補水、防呆、新鮮度可視。
- **Out of scope（本期）**：看板編輯名單、寫回相機（recordUpdater）、名單變更歷史 audit、VehicleRegisterDB（XC-204BLPR 回 400）。
- **不在本命令**：DB schema、API 合約、實作 → 交付 `/sc:design`、`/sc:workflow`。
